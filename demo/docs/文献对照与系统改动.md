## 二、本轮实际改动（可复现）

1. **架构描述视角（[8]）**
   - `demo/backend/app/services.py::architecture()` 返回 `viewpoint`：`name` / `standard` / `stakeholders` / `concerns` / `model_kinds` / `correspondences` / `references`。
   - `demo/frontend/assets/app.js::renderArchitecture()` 渲染「架构描述视角 ISO/IEC/IEEE 42010:2022」折叠卡片（两列：视点/干系人、关注点/模型种类、对应关系/依据），在架构图之上。
   - 意义：回答「你的架构视图凭什么算架构描述」——视点、关注点、模型种类、对应关系齐全，且每条对应关系都指到具体表字段。
2. **方法对照表（[6][7][9][3]）**
   - 评测页在「结构指标」与「召回率」之间新增 6 行对照（输入要求 / 输出粒度 / 控制流数据流 / 动态分派 / 部署成本 / 本课题用途），列是自研解析器、Joern、CodeQL。
   - 只写实测：例如「自研：方法内近似」「CodeQL：未接入，仅作能力边界」，不写未验证的性能结论。
3. **流水线图与 YAML（[1]–[17] 全部）**
   - `analysis-pipeline.yaml` 的 12 个 `paper` 字段改为「文献[n] + 作者年份」写法，`scripts/render_pipeline.py` 重新生成 `docs/img/pipeline-2d.svg` 与 `docs/pipeline-2d.html`。
4. **能力边界（[10]）**
   - `docs/分析过程与独创性.md` 的自查清单里补一句：Vul-LMGNNs 一类工作把图与语言模型用于漏洞检测，本系统不覆盖该任务，只在方法上借鉴「结构约束语义」。

## 三、刻意没做的（避免「为引用而引用」）

- 没有因为引用 [3] 就去做「自然语言自动生成 CPGQL」——演示环境不保证模型可用，且会破坏「结论可复现」这条不变量。
- 没有因为引用 [6][7] 就堆一张「工具评分表」——没有在同一批工程上实测 CodeQL，打分就是编的。
- 没有因为引用 [10] 就加漏洞检测模块——超出「需求与架构恢复」的课题边界，加进去反而是凑内容。
